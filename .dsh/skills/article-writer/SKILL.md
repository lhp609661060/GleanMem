# 文章撰写（article-writer）

围绕 GleanMem 项目撰写并适配技术文章，产出三个平台（公众号 / 知乎 / 掘金）的发布版本，面向技术决策者、一线开发者、行业围观人员三类受众。

## 触发场景

- 用户说「写文章」「出稿子」「准备发布内容」。
- 用户给一个主题或素材，要求适配到公众号 / 知乎 / 掘金。
- 用户要求基于某次反馈「重写 / 修改某篇文章」。

## 核心原则

1. **一条主线**：每篇文章围绕一个核心论点，默认主线是「企业记忆管理的必要性 → 问题 → GleanMem 方案 → 取舍 → 诚实边界」。
2. **用一手资料支撑，不编数字**：所有数据、设计决策、测试结果，必须从项目内**实时读取**（`docs/gleanmem/` 设计文档、`gleanmem/` 代码、`content/` 已有底稿），不要凭记忆写死数字。
3. **诚实优先**：GleanMem 是个人项目、未经大规模生产验证，这一点要在文章里如实呈现，不要吹成「生产级产品」。
4. **可反馈**：每篇结尾留 2-3 个开放问题，引导读者给出能反哺系统的反馈。

## 目录约定

```
content/
├── articles/<编号>-<主题>/
│   ├── draft.md          # 通用底稿（唯一事实源，先写这个）
│   ├── wechat.md         # 公众号版
│   ├── zhihu.md          # 知乎版
│   └── juejin.md         # 掘金版
├── feedback/<编号>-<主题>/  # 反馈收集后放这里（feedback-collector 维护）
└── index.md              # 内容索引：编号 / 主题 / 各平台发布状态 / 反馈状态
```

- 编号从 `001` 递增，一个主题一个目录。
- 先写 `draft.md` 通用底稿，再按平台拆分，避免三个版本互相漂移。
- `content/` 是 gitignore 的，绝不提交到 github。

## 三个平台的写法差异

### 公众号（受众：行业围观人员）

- 标题要有**钩子 / 反差 / 悬念**，口语化，直接点痛点。
- 开头三句内抓住人，用**场景或故事**切入，不要一上来堆术语。
- 短段落、多小标题，适配手机竖屏阅读。
- 1500–2500 字，观点鲜明，**少代码、少表格**。
- 结尾要有互动引导（提问 / 邀请反馈）。

### 知乎（受众：技术决策者 + 一线开发者 + 行业围观）

- 标题可直接点题，可用问句。
- 开头**先给结论**，再展开论证。
- 技术深度足，允许长文（3000–6000 字），论证严谨，有数据、有取舍分析。
- 重视结构化（小标题 + 列表 + 表格）。
- 结尾留开放问题引发讨论。

### 掘金（受众：一线开发者为主 + 技术决策者）

- 标题偏干货，点出具体技术点。
- **直接进入技术内容**，代码 / 数据 / 架构优先。
- 标准 Markdown，代码块规范，适合阅读实现细节。
- 2000–4000 字，突出「怎么实现的」「为什么这么设计」。
- 少情感渲染，多工程细节。

## 三个受众的关注点（写之前先想清楚）

| 受众 | 关心什么 | 写法侧重 |
|------|---------|---------|
| 技术决策者 | 值不值得引入？成本？风险？可治理性？ | 价值主张、取舍、边界 |
| 一线开发者 | 怎么用？怎么设计的？能复用吗？ | 实现细节、数据、架构 |
| 行业围观人员 | 这解决什么问题？有什么观点/故事？ | 场景、痛点、叙事 |

## 进入专业状态（关键，避免全局重新理解）

写文章时**不要**从头扫描整个项目（设计文档、代码、测试）。按以下顺序，能省则省：

1. **先读 `references/facts.md` 素材库**——它已浓缩了写文章需要的全部事实（定位、卖点、数据、决策、边界）。
2. 只有需要**核实某个具体数字或细节**时，才回项目针对性读取（`docs/gleanmem/01-design.md`、`README.md`、测试），不要通读。
3. 已有文章（`content/articles/`）能复用的论点和表述直接复用，不重写。

## 工作流

1. **读素材库**：先读 `references/facts.md`，用其中的定位、卖点、数据、边界搭建文章骨架。
2. **写 `draft.md`**：通用底稿，一条主线，论点 + 数据 + 取舍 + 边界。
3. **按平台拆分**：依据上面的平台规范，分别产出 `wechat.md` / `zhihu.md` / `juejin.md`。
4. **回报差异**：告诉用户三个版本的标题、篇幅、语气差异，以及建议的发布顺序。

## 与其他 skill 的协作

- 产出物是 `article-publisher` 的输入（发布时按平台版本投递）。
- 发布后由 `feedback-collector` 收集反馈，反馈结论可回写到本文档，用于下一轮重写。

## 写作红线

- 不编造测试数据、不虚报「生产级」「已在 XX 企业落地」。
- 引用项目外的行业数据/案例时，标注来源，无法核实的宁可不写。
- 保留「个人项目、未经大规模验证」的诚实表述。
