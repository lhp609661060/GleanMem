## 一句话定位

GleanMem（拾忆）—— 给多智能体做的**外挂长期记忆**，把散落在对话与事件里的重要信息一点一点拾起来，沉淀成可溯源、可审计的长期记忆。

## 名字含义（文章开头可讲的故事）

- 英文 GleanMem = glean（拾穗）+ memory（记忆）
- 中文「拾忆」，谐音「诗意」
- tagline：**Glean what matters · 拾起重要的**

## 核心痛点（为什么需要它）

- 企业里 Agent 越来越多，每个都「失忆」：Dify / DSH / 业务系统各记各的，换框架记忆全作废。
- 记忆的难点**不在存储**，在三个更难的问题：
  1. **什么值得记** —— 全记会膨胀，检索被陈旧信息拖垮
  2. **记错了怎么办** —— LLM 归纳出的「知识」可能是幻觉
  3. **人的修正会不会被自动更新覆盖**

## 核心卖点（4 个，文章骨架）

1. **四种接入**：Dify（MCP）/ DSH（REST 或 MCP）/ 其他 Agent（REST）/ 业务系统（推送），按 `agent_id` 隔离，一把 API Key 解决身份。
2. **召回是函数不是 Agent**：不 loop、不调工具、不让 LLM 决策，三路检索（热记忆/冷检索/Wiki）规则重排。
3. **学习延迟 + 全程审计**：`memorize` 只写收件箱，Flush 才分析；每条决策写 `learning_logs`（含 LLM 原始响应），出问题可追到是哪次推理写错了。
4. **防幻觉三道闸**：evidence 强制溯源 / `protected` 人工编辑保护 / `review_status` 审核过滤（pattern 必须 approved 才召回）。

## 关键数据（引用前到项目核实最新值）

- 中文检索：`tsvector + zhparser`，查询语义「AND 优先、空结果降级 OR」，实测自然语言召回 20/20 = 100%、p95 5.4ms（P0-3）。
- 测试用例：103 个，全绿。
- 代码库蒸馏 V1.5：batch（全量）+ event（增量）双轨，把代码库变成可检索的 Wiki 知识卡。

## 反直觉的设计决策（文章的「亮点」，最易引发讨论）

- **PostgreSQL 唯一运行时依赖**：不引入 Redis、不引入独立向量库，事件和日志都是 PG 表而非消息队列。
- **召回不用 LLM**：高频路径用规则重排，有实测数据（100% / 5.4ms）支撑，LLM 介入会让延迟和成本不可控。
- **学习延迟执行**：结尾统一分析比逐条处理更准，且天然带出审计。
- **删掉 query_db**：早期有让 Agent 直接查库的工具，后来删除并写成设计不变量——不暴露 SQL 给 LLM。

## 诚实边界（务必如实呈现，不要吹成生产级）

- 个人项目，驱动是「验证 Agent 外挂记忆这套设计思路」，**未经大规模生产流量验证**。
- 设计过程做了**三轮递进式评审**：第一轮找代码 bug → 第二轮找未验证假设 → 第三轮直接质疑「该不该做」。第三轮最狠，结论是「不要为了简历堆功能」，于是主动砍掉了过度设计的 admin UI、review 工作流、dashboard。
- 「砍掉的功能比做出来的多」是最大的收获之一。
